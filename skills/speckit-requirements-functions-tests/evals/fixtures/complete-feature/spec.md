# Feature Specification: 配送依頼連携

**Created**: 2026-08-05  
**Status**: Ready for Implementation

## Clarifications

### Session 2026-08-06

- Q: 許可する状態遷移は？ → A: 受付済み→配送中、受付済み→取消、配送中→配送済みだけを許可する。
- Q: 通知が3回失敗した後は？ → A: 隔離して5分以内に運用担当へ通知し、同じイベントIDで手動再送する。

## User Scenarios & Testing

### User Story 1 - 配送依頼を受け付ける (Priority: P1)

倉庫システムは配送依頼を登録し、依頼IDを受け取る。

**Independent Test**: 有効な依頼を1件登録し、受付済みの依頼IDが返ることを確認する。

**Acceptance Scenarios**:

1. **Given** 有効な配送先、**When** 配送依頼を登録する、**Then** 受付済みとなり依頼IDが返る。
2. **Given** 既存依頼と同じ冪等キー、**When** 再登録する、**Then** 新規作成せず最初の受付結果を返す。

### User Story 2 - 配送状態を通知する (Priority: P1)

配送状態の変更を倉庫システムへ通知する。

**Acceptance Scenarios**:

1. **Given** 受付済みの依頼、**When** 配送を開始する、**Then** 配送中イベントが発行される。
2. **Given** 3回送信に失敗したイベント、**When** 原因解消後に手動再送する、**Then** 同じイベントIDで送信される。

### Edge Cases

- 配送済みから取消への変更は拒否し、状態を変えない。
- 同じ状態変更イベントを再受信しても業務結果を重複反映しない。

## Requirements

- **FR-001**: 倉庫システムは配送先と冪等キーを指定して配送依頼を登録できなければならない。
- **FR-002**: 同じ冪等キーの再登録では依頼を重複作成してはならない。
- **FR-010**: 配送依頼はClarificationsに定義した遷移だけを許可しなければならない。
- **FR-011**: 許可されない状態遷移は現在状態を維持して拒否しなければならない。
- **FR-020**: 状態変更時にイベントID、依頼ID、変更前後の状態、変更日時を通知しなければならない。
- **FR-021**: 送信失敗時は最大3回再送し、上限到達後はClarificationsの方法で復旧できなければならない。

## Success Criteria

- **SC-001**: 登録APIの95パーセンタイル応答時間は2秒以内である。
- **SC-002**: 同一冪等キーによる重複配送依頼は0件である。
- **SC-003**: 再送上限到達から運用通知まで5分以内である。

## Assumptions

- 倉庫システムは依頼ごとに一意な冪等キーを生成する。

## Out of Scope

- 配送料金の決済。
