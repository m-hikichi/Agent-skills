FNC-001

注文の冪等受付

現行

01 注文管理 ／ 01 注文受付 ／ 01 冪等受付

認可済み外部ECから注文を受け、注文・明細・初回受付結果を同一PostgreSQL transactionに保存する。同じclientと冪等キーの同一requestには保存済み結果を返し、重複注文を作らない。

アクター
外部EC
起動契機
orders.write scopeを持つOAuth clientがIdempotency-Key付きでPOST /v1/ordersを呼び出す
実行形態
API
API-001 注文受付API
入力
  • OAuth client_id、orders.write scope
  • Idempotency-Key（1〜128文字、clientごとに30日保持）
  • externalOrderNumber（1〜64文字）
  • lines（1件以上。skuは1〜64文字、quantityは1以上）
  • destination（postalCode、address1、任意address2、recipientName）
出力
  • 初回受付: HTTP 201とOrderAccepted（orderId、status=accepted、acceptedAt）
  • 同じkey・同じpayloadの再送: HTTP 200と同じorderIdの初回受付結果
  • 失敗時: application/problem+json
事前条件
  • OAuth 2.0 client credentialsの認証とorders.write scope認可が成功している
  • 外部ECが注文ごとに一意な冪等キーを生成する
事後状態
  • 初回受付ではOrder、1件以上のOrderLine、IdempotencyResultが1 transactionで保存され、Order.statusはacceptedになる
  • 同一requestの冪等再送では新しいOrder、OrderLine、IdempotencyResultを作成しない
  • 競合または入力不正時は新しい注文を確定しない
業務ルール
  1. 注文番号、1件以上の商品明細、配送先、冪等キーを必須入力として受け付ける。 spec記載 FR-001 AC-001-01
  2. 同じclient_idと冪等キーで同じpayloadを再受信した場合は、注文を新規作成せず最初の受付結果と同じ注文IDを返す。 確認済み CL-20260621-01 FR-002 AC-001-02
  3. 冪等性はUNIQUE(client_id, idempotency_key)と正規化requestのSHA-256 hashで判定し、同じkeyでpayloadが異なる場合はHTTP 409 IDEMPOTENCY_CONFLICTとする。 設計導出 FR-002 ASM-001
    導出理由: data-model.mdのOrder/IdempotencyResult制約、research.md Decision 1、contracts/openapi.yamlの409契約を適用し、複数API replicaの並行受付でもFR-002を保証するため。
  4. 初回受付はOrder、OrderLine、IdempotencyResultを同一transactionでcommitし、一意制約競合時は先行transaction完了後に保存済み受付結果を読む。 設計導出 FR-001 FR-002 SC-002
    導出理由: plan.mdの注文登録flowとdata-model.mdのtransaction境界により、部分保存と並行重複作成を防ぐため。
  5. IdempotencyResultは30日保持し、期間経過後の同じkeyは新規要求として扱う。 設計導出 FR-002 ASM-001
    導出理由: data-model.md Retentionとcontracts/openapi.yamlのIdempotency-Key記述に明記された保持境界を適用するため。
  6. 通常想定負荷でcreateOrderの95パーセンタイル応答時間を2秒以内とする。 spec記載 SC-001
  7. 配送先、token、secretの値をapplication logへ出力しない。 設計導出 FR-001
    導出理由: plan.md Securityとdata-model.md Order.destinationの機密性制約に従い、注文受付で扱う個人情報・credentialの漏えいを防ぐため。
例外・失敗時
  • requestがOpenAPI schemaの必須項目、長さ、形式、数量制約を満たさない → HTTP 400 InvalidRequestを返し、Order、OrderLine、IdempotencyResultを保存しない。 設計導出 FR-001
    導出理由: contracts/openapi.yamlのCreateOrderRequestとInvalidRequest responseに定義されているため。
  • client認証に失敗する、またはorders.write scopeがない → HTTP 401 Unauthorizedを返し、注文データを保存しない。 設計導出 FR-001
    導出理由: contracts/openapi.yamlのsecurity schemeとUnauthorized responseに定義されているため。
  • 同じclient_id・冪等キーでrequest hashが異なる → HTTP 409 IDEMPOTENCY_CONFLICTを返し、既存注文を返さず新規注文も作らない。 設計導出 FR-002 ASM-001
    導出理由: plan.md、research.md Decision 1、contracts/openapi.yamlの競合契約に明記されているため。
対象データ
  • Order
  • OrderLine
  • IdempotencyResult

FNC-002

注文状態遷移とイベント記録

現行

01 注文管理 ／ 02 注文状態 ／ 01 状態遷移

注文の現在状態とversionを検証し、許可表にある遷移だけを実行する。成功時はOrder、OrderStateHistory、OutboxEventを同一transactionで保存し、禁止・競合時はすべて変更しない。

アクター
外部EC
起動契機
orders.transition scopeを持つOAuth clientがPOST /v1/orders/{orderId}/transitionsを呼び出す
実行形態
API
API-002 注文状態変更API
入力
  • orderId（UUID）
  • targetStatus（shipping、delivered、cancelled）
  • version（0以上）
  • triggerRef（1〜128文字）
  • OAuth client_id、orders.transition scope
出力
  • 成功: HTTP 200とOrderState（orderId、status、version、changedAt）
  • 禁止遷移: HTTP 409 INVALID_STATE_TRANSITION
  • version競合: HTTP 409 VERSION_CONFLICT
  • 対象注文なし: HTTP 404
事前条件
  • 指定orderIdのOrderが存在する
  • OAuth認証とorders.transition scope認可が成功している
  • request versionが現在のOrder.versionと一致する
事後状態
  • 許可遷移ではOrder.statusとversion、OrderStateHistory、1件のOutboxEventが同一transactionで確定する
  • 禁止遷移またはversion競合ではOrder、OrderStateHistory、OutboxEventを変更しない
  • 生成したOutboxEventはpendingとなり、Delivery Workerの配送対象になる
業務ルール
  1. 許可する遷移はaccepted→shipping、accepted→cancelled、shipping→deliveredだけとする。 確認済み CL-20260624-01 FR-010
  2. 表にない遷移と同一状態への遷移を拒否し、現在状態、履歴、Outboxを変更しない。 確認済み CL-20260624-01 FR-011 EC-001
  3. deliveredおよびcancelledを終端状態とし、deliveredからの取消要求を拒否する。 確認済み CL-20260621-02 FR-010 FR-011 EC-001
  4. 状態変更時にevent ID、order ID、変更前後状態、変更日時を持つorder.status.changed.v1のOutboxEventを1件作成する。 spec記載 FR-020 AC-002-01
  5. Order row lockとversion一致を確認し、Order、OrderStateHistory、OutboxEventを同一PostgreSQL transactionでcommitする。 設計導出 FR-010 FR-020 SC-003
    導出理由: plan.mdの状態変更flow、research.md Decision 2、data-model.md Transaction Boundariesにより、状態更新だけ成功して通知eventが失われるdual-writeを防ぐため。
  6. 初期状態acceptedのversionは0から開始し、状態変更成功ごとにversionを更新する。 設計導出 FR-010 FR-011
    導出理由: data-model.mdのOrder.versionとOrder State Transitions、contracts/openapi.yamlのrequest/response version制約を適用するため。
例外・失敗時
  • 指定したorderIdが存在しない → HTTP 404 NotFoundを返し、Order、History、Outboxを変更しない。 設計導出 FR-010
    導出理由: contracts/openapi.yamlの注文状態変更API responseに定義されているため。
  • 許可表にない遷移、終端状態からの遷移、または同一状態への遷移を要求する → HTTP 409 INVALID_STATE_TRANSITIONを返し、Order、History、Outboxを変更しない。 確認済み CL-20260621-02 CL-20260624-01 FR-011 EC-001
  • request versionと現在versionが一致しない → HTTP 409 VERSION_CONFLICTを返し、Order、History、Outboxを変更しない。 設計導出 FR-010 FR-011
    導出理由: data-model.mdのOrder.versionと禁止時のtransaction結果に定義されているため。
対象データ
  • Order
  • OrderStateHistory
  • OutboxEvent
根拠
CL-20260621-02 CL-20260624-01 US-002 AC-002-01 EC-001 FR-010 FR-011 FR-020 SC-003
FNC-003

状態変更イベント配送

現行

02 イベント連携 ／ 01 状態通知 ／ 01 外部配送

Delivery WorkerがpendingのOutboxEventをclaimし、同じevent IDをX-Event-Idとpayloadに設定して外部EC webhookへat-least-once配送する。送信結果はDeliveryAttemptへ記録する。

アクター
Delivery Worker
外部EC
起動契機
配送対象時刻に達したpendingのOutboxEventをDelivery Workerがclaimする
実行形態
外部連携
EXT-001 注文状態変更Webhook
入力
  • OutboxEvent（event_id、order_id、event_type、payload、delivery_status、next_attempt_at）
  • OrderStatusChangedEvent（eventId、orderId、previousStatus、currentStatus、changedAt）
  • X-Event-Id header
出力
  • 外部ECのHTTP response（204を成功とする）
  • DeliveryAttempt（initial/automatic/manual、結果、HTTP statusまたはerror code）
  • 成功時OutboxEvent.delivery_status=delivered、delivered_at
  • 失敗時の再試行判定用記録
事前条件
  • OutboxEventがpendingでnext_attempt_atが到来している
  • Delivery Workerが外部ECへ到達できる
  • payloadがOpenAPIのOrderStatusChangedEvent schemaに一致する
事後状態
  • HTTP 204ではOutboxEventとDeliveryAttemptを1 transactionで成功更新する
  • 送信失敗では失敗DeliveryAttemptとerror codeを記録し、FNC-004の再試行・隔離判断へ渡す
  • 再送を含むすべての配送でevent IDを変更しない
業務ルール
  1. 状態変更eventはevent ID、order ID、変更前状態、変更後状態、変更日時を必ず含み、X-Event-Idにも同じevent IDを設定する。 spec記載 FR-020
  2. OutboxEventは1件だけ発行し、network timeoutを含む再送では同じevent IDを使うat-least-once配送とする。 設計導出 FR-020 EC-003 ASM-002
    導出理由: research.md Decision 3とcontracts/openapi.yamlのX-Event-Id契約により、受信成否不明時も送信漏れを避け、外部EC側でevent ID重複排除できるため。
  3. workerはFOR UPDATE SKIP LOCKEDとlease timeoutでeventをclaimし、外部HTTP中はdatabase transactionを保持しない。 設計導出 FR-020 SC-003
    導出理由: plan.mdのDelivery Worker flowとdata-model.mdのOutboxEvent制約・transaction境界により、複数workerの同時claimと長時間lockを防ぐため。
  4. 初回・自動・手動の全送信結果をDeliveryAttemptへ記録し、response_statusまたは秘密・個人情報を含まないerror_codeを保存する。 spec記載 FR-021
  5. 外部ECは同じevent IDを複数回受信しても業務結果を重複反映せず、重複時も204を返す。 spec記載 EC-003 ASM-002
例外・失敗時
  • 外部ECが429または500を返す、またはnetwork timeoutで受信成否を確定できない → 失敗結果を記録し、event IDを変えずFNC-004の自動再送対象とする。注文状態と既存Outbox payloadは変更しない。 設計導出 FR-021 SC-003
    導出理由: contracts/openapi.yamlの一時失敗responseとresearch.md Decision 3・4により、送信漏れを避けるため。
  • workerがclaim後に停止してleaseが期限切れになる → 別workerが同じOutboxEventを再claimできるようにし、同じevent IDで再送する。 設計導出 FR-020 SC-003
    導出理由: data-model.mdのlocked_at、locked_by、lease timeout制約に定義された回復方式を適用するため。
対象データ
  • OutboxEvent
  • DeliveryAttempt
  • Order
根拠
US-002 AC-002-01 EC-003 FR-020 FR-021 SC-003 ASM-002
FNC-004

イベント自動再送・隔離・通知

現行

02 イベント連携 ／ 01 状態通知 ／ 02 障害制御

初回配送失敗後、同じevent IDを1分・5分・15分後に最大3回自動再送する。3回目の自動再送にも失敗したeventをdead-letterへ隔離し、5分以内に既存監視チャネルで運用担当者へ通知する。

アクター
Delivery Worker
運用担当者
起動契機
イベント配送が失敗する、またはpending eventのnext_attempt_atが到来する
実行形態
イベント
EVT-001 Outbox配送再試行・隔離イベント
入力
  • 失敗したOutboxEventと直近DeliveryAttempt
  • attempt_count（自動再送回数0〜3）
  • 初回失敗日時とnext_attempt_at
  • 外部EC response statusまたはerror code
出力
  • 1分・5分・15分後のnext_attempt_at
  • 各自動再送のDeliveryAttempt
  • 3回目失敗後のOutboxEvent.delivery_status=dead_letter
  • dead-letterから5分以内の運用alert（event ID、runbook linkを含む）
  • 未解決dead-letter件数・Outbox age・delivery failure metric
事前条件
  • FNC-003の配送失敗結果が記録されている
  • 再送対象のevent IDとpayloadが既存OutboxEventに保持されている
  • 既存監視通知チャネルを利用できる
事後状態
  • 再送成功時はOutboxEventがdeliveredとなる
  • 3回の自動再送失敗時は同じeventがdead_letterとなり、alert対象時刻が記録される
  • dead-letterは手動再送成功まで未解決として管理される
業務ルール
  1. 初回配送失敗から1分、5分、15分後に同じevent IDで3回自動再送する。 確認済み CL-20260624-03 FR-021
  2. attempt_countは自動再送だけを数えて0〜3とし、初回・自動再送を含む全結果をDeliveryAttemptへ記録する。 設計導出 FR-021 SC-003
    導出理由: data-model.mdのOutboxEvent.attempt_countとDeliveryAttempt定義、research.md Decision 4により、3回の再送上限と全結果記録を一貫して判定するため。
  3. 3回目の自動再送失敗transactionでOutboxEventをdead_letterへ変更し、eventを破棄しない。 確認済み CL-20260624-02 FR-022 EC-002
  4. dead-letter移行から5分以内に既存監視通知チャネルで運用担当者へ通知する。 確認済み CL-20260624-02 FR-022 SC-004 ASM-004
  5. dead-letter eventは手動再送成功まで未解決として管理し、未解決dead-letterを削除しない。 確認済み CL-20260624-02 AC-002-02 FR-022 SC-003
  6. dead-letter count、delivery failure、Outbox ageをmetric化し、dead-letter作成から5分と最古Outbox 30分をalert条件として監視する。 設計導出 FR-021 FR-022 SC-003 SC-004
    導出理由: plan.md Operational Designに定義されたmetricsとalertsで、送信漏れと通知遅延を検知可能にするため。
例外・失敗時
  • 1分または5分後の自動再送に失敗する → 失敗DeliveryAttemptを記録し、次の5分または15分後のnext_attempt_atを設定する。event IDとpayloadは変更しない。 確認済み CL-20260624-03 FR-021
  • 15分後の3回目自動再送にも失敗する → 同じeventをdead_letterへ隔離し、5分以内の運用alertを起動して手動再送成功まで未解決とする。 確認済み CL-20260624-02 CL-20260624-03 FR-021 FR-022 EC-002 SC-004
対象データ
  • OutboxEvent
  • DeliveryAttempt
根拠
CL-20260624-02 CL-20260624-03 US-002 AC-002-02 EC-002 FR-021 FR-022 SC-003 SC-004 ASM-004
FNC-005

隔離イベント手動再送

現行

02 イベント連携 ／ 02 障害復旧 ／ 01 手動再送

運用担当者が原因解消後にevent IDと操作理由を指定し、dead-letter eventを新規作成せず同じevent IDのpendingへ戻す。配送成功時にincidentと未解決状態を解消する。

アクター
運用担当者
起動契機
events.replay scopeを持つ運用担当者が原因解消を確認し、POST /v1/operations/events/{eventId}/replayを呼び出す
実行形態
API
API-003 隔離イベント手動再送API
入力
  • eventId（UUID）
  • reason（1〜512文字）
  • OAuth client_id、events.replay scope
出力
  • HTTP 202 ReplayAccepted（eventId、status=pending）
  • 手動再送のDeliveryAttemptと操作理由の監査記録
  • 配送成功後のOutboxEvent.delivery_status=delivered
  • 解消済みincidentと未解決dead-letter件数0
事前条件
  • 対象OutboxEventがdead_letterである
  • 運用担当者が外部EC側の原因解消をrunbookに従って確認している
  • OAuth認証とevents.replay scope認可が成功している
  • 操作理由が入力されている
事後状態
  • 既存OutboxEventが同じevent IDのpendingへ戻り、Delivery Workerの対象になる
  • 新しいOutboxEventを作成しない
  • 手動配送成功時に未解決dead-letterとincidentを解消する
業務ルール
  1. 原因解消後の手動再送では隔離済みeventと同じevent IDを使い、新しいeventを作成しない。 確認済み CL-20260624-02 FR-022 AC-002-02 EC-002 EC-003
  2. 手動再送APIはevents.replay scopeと1〜512文字の操作理由を必須とし、理由をDeliveryAttemptのoperator_reasonとして監査記録する。 設計導出 FR-022 ASM-004
    導出理由: plan.md Security/Recovery、contracts/openapi.yamlのreplay request、data-model.md DeliveryAttemptに定義された運用者認可と監査要件を適用するため。
  3. 手動再送成功時にOutboxEventをdeliveredへ変更し、対応incidentを解消して未解決dead-letter件数を減らす。 確認済み CL-20260624-02 AC-002-02 FR-022 SC-003
  4. 外部ECは手動再送された同一event IDを重複受信しても業務結果を重複反映しない。 spec記載 EC-003 ASM-002
