# Feature Specification: 注文連携API — 受付・状態通知・日次照合

**Created**: 2026-06-20
**Status**: Ready for planning

## Clarifications

### Session 2026-06-21

- Q: 同じ冪等キーの注文を再送した場合は？ → A: 最初の受付結果を返し、注文を重複作成しない。
- Q: 配送済みから取消へ戻せるか？ → A: 戻せない。取消要求を拒否する。

### Session 2026-06-24

- Q: 注文で許可する状態遷移は？ → A: 受付済み→配送中、受付済み→取消、配送中→配送済みだけを許可し、表にない遷移は状態を変えず拒否する。
- Q: 状態通知が3回失敗した後は？ → A: 失敗イベントを隔離し、5分以内に運用担当へ通知する。運用担当は原因解消後に同じイベントIDで手動再送し、成功まで未解決として管理する。
- Q: 再送間隔は？ → A: 初回失敗から1分、5分、15分後に再送する。
- Q: 日次02:00のタイムゾーンは？ → A: Asia/Tokyoとする。

## User Scenarios & Testing

### User Story 1 - 外部ECから注文を登録する (Priority: P1)

外部ECは注文APIを呼び出し、受付結果と注文IDを受け取る。

**Acceptance Scenarios**:

1. **Given** 正常な注文、**When** 注文APIを呼ぶ、**Then** 注文は受付済みとなり注文IDが返る。
2. **Given** 受付済みと同じ冪等キー、**When** 再送する、**Then** 新しい注文を作らず既存の受付結果を返す。

### User Story 2 - 注文状態を外部ECへ通知する (Priority: P1)

注文状態が変更されたとき、システムは状態変更イベントを外部ECへ通知する。

**Acceptance Scenarios**:

1. **Given** 受付済みの注文、**When** 出荷処理が完了する、**Then** 配送中イベントが1回発行される。
2. **Given** 3回の自動再送に失敗したイベント、**When** 原因解消後に運用担当が再送する、**Then** 同じイベントIDで送信され未解決件数が0になる。

### User Story 3 - 注文件数を日次照合する (Priority: P2)

運用担当者は、外部ECと注文連携システムの件数不一致を検知して調査できる。

**Acceptance Scenarios**:

1. **Given** 前日の件数が異なる、**When** Asia/Tokyoの02:00に照合する、**Then** 差分と対象日が運用担当へ通知される。

### Edge Cases

- 配送済み注文への取消要求は拒否し、状態を変更しない。
- 外部ECへのイベント送信に3回失敗した場合は隔離し、通知後の手動再送で復旧する。
- 同じ状態変更イベントを外部ECが複数回受信しても、イベントIDにより業務結果を重複反映しない。
- 外部ECの件数取得APIが利用できない場合は照合結果を確定せず、照合不能として通知する。

## Requirements

### 注文受付API

- **FR-001 (MUST)**: 外部ECは注文番号、商品明細、配送先、冪等キーを指定して注文を登録できなければならない。
- **FR-002 (MUST)**: 同一の冪等キーを再受信した場合、注文を重複作成せず最初の受付結果を返さなければならない。

### 状態遷移

- **FR-010 (MUST)**: 注文状態はClarificationsに定義した許可遷移だけに従って変更されなければならない。
- **FR-011 (MUST)**: 許可表にない遷移要求を拒否し、現在状態を維持しなければならない。

### イベント連携

- **FR-020 (MUST)**: 注文状態が変わった場合、イベントID、注文ID、変更前後の状態、変更日時を含むイベントを外部ECへ送信しなければならない。
- **FR-021 (MUST)**: イベント送信失敗時はClarificationsの間隔で最大3回再送し、全結果を記録しなければならない。
- **FR-022 (MUST)**: 再送上限到達後はイベントを隔離し、5分以内に運用担当へ通知し、同じイベントIDによる手動再送で解消できなければならない。

### 日次照合

- **FR-030 (MUST)**: システムは毎日02:00 Asia/Tokyoに外部ECの前日注文件数と内部注文件数を照合し、不一致または照合不能を運用担当者へ通知しなければならない。

### 将来対応

- **FR-040 (SHOULD)**: 【将来対応】注文変更履歴を外部ECから検索できるAPIを提供すべきである。

## Success Criteria

- **SC-001**: 注文APIの95パーセンタイル応答時間は2秒以内である。
- **SC-002**: 同一冪等キーによる重複注文は0件である。
- **SC-003**: 状態変更イベントの未解決送信漏れは0件である。
- **SC-004**: 再送上限到達から運用担当への通知まで5分以内である。

## Assumptions

- 外部ECは注文ごとに一意な冪等キーを生成する。
- 外部ECはイベントIDで受信イベントを重複排除する。
- 日次照合用の件数取得APIは外部ECから提供される。
- 運用担当者は既存の監視通知チャネルを利用できる。

## Out of Scope

- 決済処理と返金処理は本機能の対象外とする。
- 注文変更履歴API（FR-040）は将来バージョンで提供する。
- 外部EC内部のイベント処理方式は対象外とする。
