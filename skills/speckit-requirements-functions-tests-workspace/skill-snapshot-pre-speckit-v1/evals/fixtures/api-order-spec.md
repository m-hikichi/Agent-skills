# Feature Specification: 注文連携API — 受付・状態通知・日次照合

**Created**: 2026-06-20
**Status**: Draft

## Clarifications

### Session 2026-06-21

- Q: 同じ冪等キーの注文を再送した場合は？ → A: 最初の受付結果を返し、注文を重複作成しない。
- Q: 配送済みから取消へ戻せるか？ → A: 戻せない。取消要求を拒否する。

## User Scenarios & Testing

### User Story 1 - 外部ECから注文を登録する (Priority: P1)

外部ECは注文APIを呼び出し、受付結果と注文IDを受け取る。

**Acceptance Scenarios**:

1. **Given** 正常な注文、**When** 注文APIを呼ぶ、**Then** 注文は受付済みとなり注文IDが返る。
2. **Given** 受付済みと同じ冪等キー、**When** 再送する、**Then** 新しい注文を作らず既存の受付結果を返す。

### User Story 2 - 注文状態を外部ECへ通知する (Priority: P1)

注文状態が変更されたとき、システムは状態変更イベントを外部ECへ通知する。

**Acceptance Scenarios**:

1. **Given** 受付済みの注文、**When** 出荷処理が完了する、**Then** 配送中イベントが1回発行される。

### Edge Cases

- 配送済み注文への取消要求は拒否し、状態を変更しない。
- 外部ECへのイベント送信に失敗した場合は最大3回まで再送する。

## Requirements

### 注文受付API

- **FR-001 (MUST)**: 外部ECは注文番号、商品明細、配送先、冪等キーを指定して注文を登録できなければならない。
- **FR-002 (MUST)**: 同一の冪等キーを再受信した場合、注文を重複作成せず最初の受付結果を返さなければならない。

### 状態遷移

- **FR-010 (MUST)**: 注文状態は「受付済み」「配送中」「配送済み」「取消」の順序と許可条件に従って遷移しなければならない。
- **FR-011 (MUST)**: 配送済み注文への取消要求を拒否し、現在状態を維持しなければならない。

### イベント連携

- **FR-020 (MUST)**: 注文状態が変わった場合、注文ID、変更前後の状態、変更日時を含むイベントを外部ECへ送信しなければならない。
- **FR-021 (MUST)**: イベント送信失敗時は最大3回まで再送し、結果を記録しなければならない。

### 日次照合

- **FR-030 (MUST)**: システムは毎日02:00に外部ECの注文件数と内部注文件数を照合し、不一致を運用担当者へ通知しなければならない。

### 将来対応

- **FR-040 (SHOULD)**: 【将来対応】注文変更履歴を外部ECから検索できるAPIを提供すべきである。

## Success Criteria

- **SC-001**: 注文APIの95パーセンタイル応答時間は2秒以内である。
- **SC-002**: 同一冪等キーによる重複注文は0件である。
- **SC-003**: 状態変更イベントの最終的な送信漏れは0件である。

## Assumptions

- 外部ECは注文ごとに一意な冪等キーを生成する。
- 日次照合用の件数取得APIは外部ECから提供される。

## Out of Scope

- 決済処理と返金処理は本機能の対象外とする。
- 注文変更履歴API（FR-040）は将来バージョンで提供する。
