# HTML 書式仕様 & JSON スキーマ詳細

このスキルは社内 Excel テンプレート `○○_基本設計_機能一覧.xlsx` の見え方を **HTML** で
再現し、さらに「機能/要件の分離」「画面紐付け」「シートタブ切替」を加えたもの。書式は
`scripts/build_design_html.py` に内蔵済み。ここはその**根拠**と、JSON データの**細部**、
分解の**解像度サンプル**をまとめた参照資料。書式を手で再現する必要はない。

## なぜ単一 HTML なのか（設計意図）

成果物は 1 ファイルで「**Excel と同じ雰囲気の資料**」と「**git で差分が読めるソース**」を
兼ねる。これを成立させるための実装上の約束:

- **インライン style を使わない**。色・結合・寄せはすべて `<style>` 内の CSS クラス
  （`dai`/`chu`/`sho0`/`sho1`/`g`/`rule`/`scrcol`/`frcol`/`future`）で付ける。→ 各行が
  「中身の変化」だけで動き、style 文字列のノイズが diff に出ない。
- **1 機能行 = HTML 1 行**。`<tr>…</tr>` を 1 行に収める（業務ルールの箇条書きや画面の
  複数紐付けも `<br>` で 1 行内に畳む）。→「概要やルールを 1 か所直した」が「diff 1 行」になる。
- **大/中/小分類はグループ先頭行にだけ rowspan セルを置く**（Excel のセル結合と同じ見え方）。
  行を 1 つ足すと、そのグループ先頭の rowspan 数字と追加行だけが変わる、局所的な diff になる。
- **決定的出力**。同じ design.json からは毎回バイト同一の HTML が出る。
- **自己完結**（CSS/JS 内蔵・外部アセット無し・フォントはシステムの游ゴシックにフォール
  バック）。メール添付・別マシン閲覧でも崩れない。

## 機能一覧の書式

| 要素 | 仕様 |
|---|---|
| フォント | 游ゴシック系。本文 13px、タイトル 26px |
| 列 | 大分類 / 大分類ID / 中分類 / 中分類ID / 小分類 / 小分類ID / **機能名** / **概要** / **業務ルール** / **画面** / **要求ID** |
| ヘッダ行 | 塗り `#C6D9F1`、中央寄せ、`position:sticky`（タブバーの下に張り付き、長い表でも列が見える） |
| 塗り分け | 大分類=`#4BACC6`（Aqua Accent5）／中分類=`#92CDDC`（明るく40%）／小分類=`#DAEEF3`(accent5明るく80%)と`#FDE9D9`(accent6明るく80%)を隣接小分類で交互。機能名以降は白 |
| セル結合 | 同一 大/中/小分類が複数行に渡るとき、グループ先頭行に `rowspan` 付きセル（名前列＋ID列）。ID 列は中央寄せ |
| 機能名 | 体言止めの機能名。将来対応行は前に `将来対応` バッジ |
| 概要 | その機能が**何をするか**（1文。条件・ルールは入れない） |
| 業務ルール | 条件・制約・要件を `・` の箇条書き（配列を 1 行内に `<br>` 連結） |
| 画面 | `SCR-020 予約入力画面` のように画面マスタを解決して表示（SCR-id は淡色バッジ）。複数可。横断機能は「全画面共通」 |
| 要求ID | 由来 FR（淡色・中央）。複数なら "FR-061, FR-062" |
| 列幅 | `<colgroup>` で相対指定（業務ルールが最も広い）。`table-layout:fixed`＋折返し |
| 印刷 | `@media print` でタブを隠して全シートを通しで出力、ヘッダを各ページに繰り返し、行の途中改ページ抑止。ブラウザの「PDF として保存」で配布物になる |

色は Excel テンプレートの実テーマ（Office 既定: accent5=`#4BACC6`、accent6=`#F79646`）を
採用し、中/小分類は Excel の「明るく 40%/80%」相当の tint を当てた値。→ 既存 Excel と同じ
teal 系の段階塗りになる。

## シート（タブ）構成

Excel の各シートを HTML 上部の**タブ**で切り替える（クリックで表示シートを切替、アクティブは
テーマ色で強調、タブは sticky で常に見える）。データがあるシートだけ出る。

| タブ | 由来 | JSON キー |
|---|---|---|
| 機能一覧 | Excel ① | `function_list`（必須） |
| 画面一覧（画面マスタ） | 本スキルで追加 | `screens` |
| ユーザーストーリー | Excel ② | `user_stories` |
| 成功基準ほか（成功基準・前提・対象外） | Excel ③ | `criteria` |
| データエンティティ | Excel ④ | `entities` |

`screens` を省略すれば Excel と同じ 4 シート相当になる。各 `<h2>`/パネルには `id`
（`func`/`screens`/`us`/`crit`/`ent`）が付く。印刷時は全パネルを表示しシート毎に改ページ。

## 将来対応の見せ方

「v1対象外」のような打ち消し表現は使わない。将来バージョンで提供予定のものは
**「将来対応」**として淡色＋バッジで控えめに示す（"やらない"ではなく"あとでやる"）。

- 機能行: `row` に `"future": true`（後方互換で `将来`/`out_v1`/`対象外` も可）。淡いグレー
  背景＋機能名前に `将来対応` バッジ。**取消線は使わない**。
- 配下の全 row が将来対応の 大/中/小分類は、その見出しセルも淡色になる。
- 画面マスタ: 画面に `"out_v1": true`（または `future`）で画面名に「（将来対応）」が付く。

## JSON スキーマ詳細

トップレベル:

| キー | 必須 | 説明 |
|---|---|---|
| `output` | △ | 出力パス。`.html` 推奨。`.xlsx` 等でも拡張子を `.html` に置換。`-o` で上書き可 |
| `output_html` | 任意 | HTML 専用の出力パス（xlsx と HTML を同じ design.json から出す運用向け） |
| `title` | 任意 | タイトル（既定 "機能一覧"） |
| `meta` | 任意 | `作成日`/`作成者`/`更新日`/`更新者`。日付は `YYYY-MM-DD`/`YYYY/MM/DD`（`YYYY年MM月DD日` に整形） |
| `screens` | 任意 | 画面マスタ（あれば「画面一覧」タブを生成し、`画面` 列の SCR-id を解決） |
| `function_list` | **必須** | 大分類の配列（下記） |
| `user_stories` / `criteria` / `entities` | 任意 | 補助シート用 |

`screens`（画面マスタ）:

```
screens: [ {"id": "SCR-001", "name": str, "summary": str(任意), "roles": str(任意), "out_v1": bool(任意)} ]
```

`function_list`（3階層 + rows）:

```
function_list: [ 大分類 ]
大分類 = { "name": str, "id": str, "children": [ 中分類 ] }
中分類 = { "name": str, "id": str, "children": [ 小分類 ] }
小分類 = { "name": str, "id": str, "rows": [ 機能行 ] }
機能行 = {
  "機能名": str,            # = 細分類（体言止め）
  "概要": str,             # 何をするか（1文）
  "業務ルール": [str, ...], # 条件・制約・要件（箇条書き）
  "画面": [str, ...],       # 画面マスタの id（"全画面共通" など自由文字列も可）
  "FR": str,               # 由来 FR（"FR-061, FR-062" のように複数可）
  "future": bool(任意)      # 将来対応なら true
}
```

- `id` は各階層内での連番（"01","02"…）。
- **後方互換**: `機能名` が無ければ `細分類` を、`業務ルール`/`画面` が無ければ旧スキーマ
  （`機能`→概要、`概要`→業務ルール1項目、画面=空）として描画する。新規・更新では新スキーマで書く。
- `criteria` の `区分` は "成功基準"/"前提"/"対象外" を想定。

## サンプル行（解像度の基準）

要求を「写経」しただけか、ちゃんと設計に「引き上げ」たうえで**機能/要件を分離し画面を
紐付けた**かの判断基準。下は spec.md の `FR-021`（指定期間の予約数が利用可能在庫数を
超える場合は予約を拒否）を分解した例（小分類「予約受付」配下、画面=SCR-020）。

| 機能名 | 概要 | 業務ルール | 画面 | 要求ID |
|---|---|---|---|---|
| 予約期間妥当性チェック | 利用開始日時が終了日時より前かを検査する | ・開始日時が終了日時以降なら入力エラー ・エラー時は予約登録しない | SCR-020 | FR-020 |
| 期間重複予約検索 | 同じ備品の指定期間と重なる予約を検索する | ・取消済み予約は集計対象外 ・貸出中データも重複対象に含める | SCR-020 | FR-021 |
| 利用可能在庫数算出 | 指定期間に予約可能な在庫数を算出する | ・総在庫から点検中・故障を除外 ・重複予約数を差し引く | SCR-020 | FR-021, FR-024 |
| 予約可否判定 | 利用可能在庫数に基づいて予約の受付可否を決める | ・在庫数を超える場合は予約拒否 ・拒否時は代替期間を案内 ・在庫があれば予約番号を発行 | SCR-020 | FR-020, FR-021 |

ポイント:
- 1つのFRが複数機能に分解されている。
- **概要**＝「何をするか」1文、**業務ルール**＝判定条件・エラー時挙動・受理ルール、と
  明確に分離（旧来これらを 1 つの「概要」に混ぜていたのを分けた）。
- 全機能に**画面**（SCR-090）と**要求ID**が紐づく。
- 将来提供する機能を例示する場合は `future: true` を付け、淡色＋バッジで区別する。

`機能` 列に要求文をそのまま貼っただけ（概要＝要求文の丸写し・業務ルール空・画面なし）は
分解不足のサイン。
