# 基本設計書(機能一覧) HTML 生成スキル

## このスキルがやること（と、なぜ HTML なのか）

Spec Kit の `spec.md`（ユーザー要求・機能要件・受入条件を記述した **Feature Specification**）
のような要求・要件定義成果物を入力に、社内 Excel テンプレートと同じ
見え方の**基本設計書（機能一覧）を単一の自己完結 HTML ファイル**として出力する。

### 入力となる `spec.md` の位置づけ

Spec Kit の `spec.md` は `/speckit.specify` が生成する **Feature Specification** であり、
基本設計書や実装計画書ではない。ユーザーストーリー、受入シナリオ、エッジケース、機能要件
（FR）、主要エンティティ、成功基準、前提などを記載し、**何を作るか／なぜ必要か（What/Why）**
に焦点を置く。技術スタック、アーキテクチャ、API 契約、詳細なデータモデルなどの実装方針は、
後続の `/speckit.plan` が `plan.md` 等へ記載する。

日本語の一般的な開発工程に当てはめると、`spec.md` はユーザー要求を整理する**要求定義**と、
システムが満たす機能や受入条件を定める**要件定義**の両方にまたがる成果物と捉えるのが近い。
単なる要求一覧より具体的だが、基本設計そのものではない。

このスキルは `spec.md` に書かれたユーザー要求・機能要件・受入条件を読み、基本設計レベルの機能構成、業務ルール、
画面対応へ具体化する。`plan.md` や `tasks.md` は主入力ではないが、利用者が補足資料として指定した
場合は、`spec.md` と矛盾しない範囲で設計判断の参考にしてよい。

なぜ Excel(.xlsx) ではなく HTML なのか——**2 つの要求を 1 つの成果物で両立できる**から。

| 要求 | Excel(.xlsx) | この HTML |
|---|---|---|
| 誰でも見やすい資料（大→中→小を俯瞰、セル結合・色分け・游ゴシック・シート切替） | ◎ | ◎（ブラウザで同じ見え方／上部タブで切替／印刷で PDF） |
| git で更新差分が確認できる | ✗（バイナリ、差分が読めない） | ◎（1 機能行＝1 行、変更が日本語のまま diff に出る） |

つまり成果物は「**Excel と同じ雰囲気で読める資料**」であり、かつ「**テキストとして
差分が追えるファイル**」でもある。ソースと資料が同一なので、別途 md/yaml を管理する
必要はなく、レビュアーは PR の diff で「どの機能の概要／業務ルールがどう変わったか」を
そのまま読める。

### 機能一覧の列（重要）

レビューしやすさのため「機能」と「要件」を分離し、画面紐付けを持つ。

| 列 | 中身 |
|---|---|
| 大分類 / 中分類 / 小分類（＋各ID） | 機能の階層（セル結合・テーマ色で俯瞰） |
| **機能名** | 機能の名前（体言止め。例「ログイン認証」） |
| **概要** | その機能が**何をするか**を簡潔に1文（ルールは書かない） |
| **業務ルール** | 条件・制約・要件・バリデーション・エラー時/境界時の挙動・既定値（箇条書き） |
| **画面** | この機能が使われる画面（画面マスタの SCR-xxx を紐付け。横断機能は「全画面共通」） |
| **要求ID** | 由来する FR（トレーサビリティ） |

> **設計の肝**: 旧来「概要」に混在しがちな「何をするか（機能）」と「どういう条件か
> （要件）」を **概要** と **業務ルール** に切り分ける。これがレビューのしやすさを決める。

重要な前提: **Feature Specification（要求・要件定義成果物） ≠ 機能一覧**。
両者は抽象レベルが違う。

| | Feature Specification（spec.md） | 機能一覧（基本設計書） |
|---|---|---|
| 性質 | 要求・要件（What/Why、実装技術非依存） | 機能構成・業務ルール・画面対応への具体化 |
| 視点 | 利用者・ビジネス | 設計者・開発者 |
| 例 | 「システムは予約時に在庫数を超えないことを検証しなければならない」 | 「期間重複検索」「予約数集計」「在庫上限判定」「予約拒否」「代替期間案内」 |

このスキルの核心は単なるセル詰めではなく、**各機能要件(FR)を基本設計レベルの具体的な
機能群へ分解・詳細化し、機能/要件を分離し、画面へ紐付ける設計作業**にある。書式・HTML 化は
スクリプトに任せ、頭はこの分解・分離・紐付けに使う。

## 全体の流れ

1. 入力の仕様書（既定では speckit の `spec.md`）を読む。**更新の場合は既存の成果物
   （`機能一覧.html`）も読み**、既にある構造・文言を尊重して差分を最小に保つ（後述「更新時」）。
2. **画面マスタを起こす**（後述「画面マスタの作り方」）。spec.md から画面（SCR-xxx）を抽出。
3. **設計への引き上げ**を行う（後述「設計分解の方法」）。FR を機能・処理へ分解し、
   大分類→中分類→小分類→機能名 の階層に整理し、各機能を 概要／業務ルール に分け、画面を紐付ける。
4. 補助シート用に User Stories / Success Criteria・Assumptions・Out of Scope /
   Key Entities を構造化する。
5. 設計データを 1 つの JSON（`design.json`）にまとめる。
6. `scripts/build_design_html.py` で自己完結 HTML を生成する。
7. 生成物を検証する（後述「生成と検証」）。HTML はそのまま git 管理する成果物。

> `design.json` は**生成の入力（中間ファイル）**。git に残す成果物は **HTML 一本**でよい。
> `scripts/build_design_html.py` 自体は `spec.md` を解析しない。エージェントが `spec.md` を読んで
> `design.json` を作成し、スクリプトはその構造化データを決定的に HTML へ描画する。

## 設計分解の方法（このスキルの肝）

要求を機能一覧に「写経」しただけの成果物は価値が低い。読み手（設計者・実装者）が
そのまま実装に着手できる粒度まで具体化する。原則は次の通り。

- **1つのFRは複数の機能に分かれることが多い。** 「〜を検証する」「〜を生成する」と
  いった要求は、内部的には複数の処理ステップに分解できる。動詞で切り出す
  （読込・判定・変換・集約・出力・例外処理…）。
- **`機能名` = 具体的な処理単位の名前**（体言止め。例:「在庫上限チェック」）。
- **`概要` = その機能が何をするか**を簡潔に1文（例:「指定期間の予約数が在庫数を超えないか検査する」）。
  **ここに条件・ルールを混ぜない**——それは業務ルールへ。
- **`業務ルール` = 要件・条件・制約**（配列＝箇条書き）。判定条件・しきい値・
  エラー時/境界時の挙動・既定値・出力メッセージ・参照する他機能・前提 など、
  「実装で守るべきこと」を1項目ずつ。実装レベルの具体（「在庫数を超える場合は予約を拒否」
  「貸出開始後は予約取消不可」等）まで踏み込む。MUST 以外は末尾に `(SHOULD)`/`(MAY)`、
  判断保留は `要確認` を付す。
- **`画面` = この機能が使われる画面**（画面マスタの SCR-xxx）。予約系→予約入力画面、
  管理系→備品管理画面 のように、機能の実態に合う画面を選ぶ。複数画面にまたがる
  なら複数列挙。認証・データ分離・内部集計など特定画面に紐づかない横断機能、および
  **バックエンド/バッチ/自動処理など操作画面を持たない機能は「全画面共通」**にする
  （関連する管理画面があっても、その管理画面は利用者が直接操作する機能にだけ紐付ける）。
- **`要求ID`（FR）= トレーサビリティ。** 各機能に由来する FR を必ず付ける。
  複数FR由来なら "FR-061, FR-062" のように列挙。設計が要求へ追跡できることは必須品質。
- **要求にない実装を勝手に増やしすぎない。** 分解は要求を満たすために必要な範囲に
  とどめ、過度な推測は避ける。判断に迷う箇所は `業務ルール` に「要確認」と明示。
  spec.md の Clarifications/Assumptions は設計判断の根拠として活用する。

### 階層のマッピング指針

- `大分類` … 機能領域の最上位（例: 備品利用 / 貸出管理）。spec.md の大きな括りや
  処理フェーズで分ける。
- `中分類` … spec の**要件をグルーピングしている見出し**に対応（`####` があればそれ、
  無ければ `###` 等、その spec で要件を束ねている最下層の見出し）。見出しの深さは spec ごとに
  違うので、深さ（###/####）ではなく「要件を束ねている単位」で中分類を取る。
- `小分類` … 中分類内の sub-feature。1つのFR群や、ビジュアル部/明細部のような区分。
- `機能名`/`概要`/`業務ルール`/`画面` … 上記の分解で得た**設計レベルの末端機能**。

迷ったら「`references/format_spec.md` のサンプル行と同じ解像度になっているか？」を
基準にする。概要が要求文の丸写しで、業務ルールが空なら、まだ分解が足りない。

### 判断に迷うときの既定ルール

executor が毎回違う答えを出すと成果物が安定しない（＝無駄な diff が出る）ので、迷ったら
次の既定に従う（spec.md に明示があればそちらを優先）。

- **横断的なFRの配置**：主たる処理フェーズの `大分類` に1回だけ置く。トレーサビリティ
  のため関連機能の `FR` に同番号を併記してよい（複数行に同一FRが出るのは正常）。
- **要求レベル(MUST/SHOULD/MAY)**：MUST 以外は該当する `業務ルール` 末尾に
  `(SHOULD)`/`(MAY)` を付す。MUST は無印。
- **spec.md に無い `大分類`/`中分類` を新設しない**：必要なら新設し、その機能の `業務ルール`
  に「(spec外・実装都合で追加)」と明示する。

### 将来対応（将来バージョン）の扱い

spec.md が「将来／対象外」と明示する要件は、機能一覧から消さずに**将来対応として
残す**（将来の設計の足場になり、判断記録にもなる）。該当 row に `"future": true` を付けると、
スクリプトが淡いグレー＋「将来対応」バッジで控えめに区別し（取消線は使わない＝"やらない"
ではなく"あとでやる"の見せ方）、機能名の前に `将来対応` を付す。配下の全 row が将来対応なら
その大/中/小分類の見出しセルも淡色になる。画面マスタ側の将来画面は `"out_v1": true`
（または `future`）で「（将来対応）」表示になる。

## 画面マスタの作り方

`画面` 列の紐付け先を、spec.md から起こす。各画面は `{id, name, summary, roles, future?}`。

- `id` … `SCR-001` のような連番（領域ごとに桁を空けて採番すると後から足しやすい）。
- `name` … 画面名（例「認識結果編集画面」）。
- `summary` … 何をする画面か（1行）。
- `roles` … 主な対象ロール（例「利用者」「利用者／管理者」「管理者」）。
- `future` / `out_v1` … 将来バージョンの画面なら true（「（将来対応）」表示）。

spec.md の User Story・FR・Clarifications から「画面」に相当するものを拾う（検索画面・
予約入力画面・一覧画面・管理画面・設定画面 等）。粒度は「利用者が認識する1画面」を
目安にし、過度に細分化しない。粒度で迷ったときの既定: **一覧画面と、その項目を操作する
詳細/編集画面は別レコードに分ける**（spec が1画面と明示する場合を除く）。逆に、**同一画面内の
段階（入力→確認 等のフェーズ）は1画面にまとめる**。各機能の `画面` 列はこのマスタの `id` を参照する。
**画面マスタに載せる画面は、最低1つの機能から参照されるものに限る**（どの機能からも参照されない
画面は作らない＝機能↔画面の双方向トレース）。なお画面粒度は設計判断であり、上の既定で機械的に
決めてよい（多少割れても致命的ではないので、迷ったら既定に従って確定し、深追いしない）。

## JSON 設計データの作り方

`scripts/build_design_html.py` は次の構造の JSON を消費する（詳細とサンプルは
`references/format_spec.md`）。`function_list` は必須、`screens`・補助3キーは任意
（既定では spec.md に該当情報があれば全て埋める）。

```json
{
  "output": "specs/<feature>/<タイトル>_基本設計_機能一覧.html",
  "title": "<プロダクト名>　機能一覧",
  "meta": {"作成日": "YYYY-MM-DD", "作成者": "氏名", "更新日": "YYYY-MM-DD", "更新者": "氏名"},
  "screens": [
    {"id": "SCR-001", "name": "ログイン画面", "summary": "利用者認証・ログイン", "roles": "全ロール"},
    {"id": "SCR-050", "name": "利用実績画面", "summary": "...", "roles": "管理者", "out_v1": true}
  ],
  "function_list": [
    {"name": "大分類名", "id": "01", "children": [
      {"name": "中分類名", "id": "01", "children": [
        {"name": "小分類名", "id": "01", "rows": [
          {"機能名": "処理名", "概要": "何をするか1文",
           "業務ルール": ["条件1", "制約2 (SHOULD)"],
           "画面": ["SCR-001"], "FR": "FR-001", "future": false}
        ]}
      ]}
    ]}
  ],
  "user_stories": [
    {"id": "US1", "story": "...", "priority": "P1", "scope": "...", "summary": "...", "acceptance": "1) ... 2) ..."}
  ],
  "criteria": [
    {"区分": "成功基準", "項目": "SC-001", "内容": "..."},
    {"区分": "前提",     "項目": "...",    "内容": "..."},
    {"区分": "対象外",   "項目": "...",    "内容": "..."}
  ],
  "entities": [ {"name": "エンティティ名", "desc": "説明"} ]
}
```

- `meta` … `作成日`は spec.md の Created、`更新日`は本日。作成者/更新者は
  **spec に記載があればそれ → 無ければ git の user.name → それも無ければ空欄**、の優先順で決める。
- HTML 上部のタブは、データがあるシートだけ出る（機能一覧／画面一覧／ユーザーストーリー／
  成功基準ほか／データエンティティ）。`screens` を省けば Excel と同じ4シート相当になる。
### 補助シート・画面一覧の生成（裁量で揺れないための既定）

「作る/作らない」で出力がブレないよう既定を固定する（spec に対応情報があるのに省略しない）:
- **ユーザーストーリー** … spec に User Stories があれば**必ず**生成。
- **成功基準・前提・対象外** … spec の Success Criteria / Assumptions / Out of Scope を
  **必ず**1シートに束ねて生成。`criteria` の `区分` は節に対応させる:
  **Success Criteria→「成功基準」／Assumptions→「前提」／Out of Scope→「対象外」**。
- **データエンティティ** … spec に Key Entities 節があればそれを使う。**節が無くても** spec の
  Requirements・Assumptions・状態・マスタ等から主要データエンティティ（名詞・状態・マスタ）を
  抽出して生成する（基本設計に有用なため。trivial で無意味なときのみ省略し、その判断を残す）。
- **画面一覧（画面マスタ）** … 本スキルは `画面` 列を持つので**常に**生成する。

### 出力先とファイル名（呼び出し側の指定を優先・区切り欠落に強く）

- 既定は `<対象>_基本設計_機能一覧.html` を **spec.md と同じフォルダ**に置く。
- **呼び出し側が出力先（ディレクトリ/パス）を明示したら、その指定を既定より優先する。**
  design.json の `output` キーをそのパスにし、`-o` でも上書きできる（両方そろえると確実）。
- `<対象>` は見出し（`# Feature Specification: …`）の製品名部分。既定は「`:` の後ろ 〜
  最初の `—` の前、丸括弧注記は除去」（例: 「備品貸出管理デモ（試作版） — 予約・返却」→ `備品貸出管理デモ`）。
  **区切りが欠けても破綻させない**: `:` が無ければ `Specification` の後ろ全体、`—` が無ければ
  `:` 以降の残り全体を採用する。**先頭/末尾の空白は除去**し語中の空白は保持、日本語はローマ字化しない。

> **後方互換**: 旧スキーマ（`細分類`/`機能`/`概要` のみ。basic-design-xlsx 由来）も描画でき、
> その場合 概要=旧機能、業務ルール=[旧概要]、画面=空 として表示する。新規・更新では必ず
> 新スキーマ（機能名・概要・業務ルール・画面）で書く。

## 生成と検証

```bash
python <skill>/scripts/build_design_html.py design.json
# または出力先を明示
python <skill>/scripts/build_design_html.py design.json -o "specs/.../備品貸出管理デモ_基本設計_機能一覧.html"
```

生成後、最低限これを確認する:

- **全 FR が機能一覧のどこかに `要求ID` として現れているか**（要求の取りこぼし防止）。
  「全 FR」は **spec に実在する FR 番号すべて**を指す（連番の穴は気にしない・存在しない番号を
  作らない）。要求ID の集合が spec の FR 集合と一致するかで確認する。
- **各機能に画面が紐づいているか**（`画面` 列が空でないか）。SCR-id が画面マスタに存在するか。
  スクリプトが表示する `機能一覧 N行` は**将来対応を含む全機能行数（rows の総数）**なので、
  spec から数えた想定機能数と突き合わせる自己チェックに使える。
- **概要と業務ルールが分離されているか**（概要に条件が混ざっていないか、業務ルールが空でないか）。
- 期待どおりのタブ（機能一覧／画面一覧／ユーザーストーリー／成功基準ほか／データエンティティ）が
  出ているか。
- ブラウザで開いて、タブ切替・大→中→小のセル結合・テーマ色・タイトル/メタ枠が崩れていないか
  （`open 出力.html`）。
- **差分の健全性**：更新時は `git diff` を見て、意図した行だけが変わっているか確認する。
  無関係な行が大量に動いていたら分解の揺れが原因。既存文言を尊重して書き直しを最小化する。

書式（フォント・色・結合・列幅・タブ・印刷用 CSS）はスクリプトに内蔵済み。色は Excel
テンプレートの実テーマ色（accent5=teal / accent6=orange、中/小は明るく 40%/80%）を採用。

## 更新時（差分を最小に保つ）

このスキルの価値は「更新差分が読めること」。更新では**作り直しではなく最小編集**を狙う。

- **小さな文言修正**（概要や業務ルール1項目の修正）：生成済み HTML の該当 `<td>` を直接
  編集してよい（1 行＝1 機能行なので diff も 1 行）。または design.json を直して再生成。
- **機能の追加・FR の新設**：design.json に当該 row/小分類を追記し、**既存行の文言は
  極力変えずに**再生成する。追記分とその所属グループの rowspan 数だけが変わる読みやすい diff。
- **画面の追加・改称**：`screens` を直す。`画面` 列は id 参照なので名前変更は1か所で済む。
- **再生成で無駄な diff を出さない**：spec 全体から作り直すと分解の揺れで無関係な行まで
  文言が変わりがち。更新時は既存の HTML/design.json を**正**として読み、変える箇所だけに手を入れる。
