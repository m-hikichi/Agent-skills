## 主要エンティティ

- 表示サイズ（CharacterScale）: キャラクターをどの大きさで表示するかを表すユーザー設定。 標準サイズ（100%）に対する比率で表し、75%・100%・125%・150% のいずれかの値をとる。 アプリ全体で1つだけ存在し、アプリの設定として保存される。（spec.md#L334）
- 位置（CharacterPosition）: キャラクターが画面上のどこにいるか。キャラクターの 下辺中央（足元アンカー）を、スクリーン座標（FR-022。物理ピクセル座標と一致）の実数で 表す。サイズが変わってもこの値は変わらず、ウィンドウの左上は「足元アンカー − 論理座標のオフセット × 表示倍率」で毎回導出する。001 と同じく保存・復元される。（spec.md#L337）
- 状態（CharacterState）: ペットが今どういう状況にあるか（待機している／ドラッグで 運ばれている）と、ペットの向き（最後に左右へ動かされた方向。初期値は右向き）。（spec.md#L341）
- 再生中のアニメーション（CurrentAnimation）: 今どのアニメーションのどのコマを 再生しているか。本機能以降に使用するのは「待機」「右向きの走り」「左向きの走り」の3つ。 手振り・ジャンプなど他のアニメーションはペットパッケージには含まれ続けるが、再生されない。（spec.md#L343）
- ドラッグ操作: ユーザーがキャラクター本体をつかんでから離す（または中断される） までの一連の操作。進行中は、直近の左右の移動方向と、カーソルが動いているかどうかによって 再生するアニメーション状態が決まる。（spec.md#L346）

## Summary

001 で実装した「ランダムな間隔で小移動・しぐさを抽選する」挙動を廃止し、ペットは
普段つねに idle 行をループする。ユーザーがドラッグで動かしている間だけ、進行方向に応じて
running-right / running-left を再生する（0.3秒静止で idle に復帰、上下のみの移動では
保持している向きで走る）。あわせて、常駐メニューから表示サイズを 4段階
（Small 75% / Medium 100% / Large 125% / X-Large 150%）で切り替えられるようにし、
設定を永続化する。

技術アプローチは 001 の構成（C# / .NET 10 + Avalonia UI 11）をそのまま使い、
**依存の追加は行わない**。中心となる設計は次の3点:

1. **状態の4分割**（ユーザー指定）: `CharacterScale` / `CharacterPosition` /
   `CharacterState` / `CurrentAnimation`（= 既存 `AnimationEngine`）を独立した値として
   持ち、ウィンドウの矩形はそこから**導出**する。サイズ変更は `CharacterScale` だけを
   書き換えるので、再生中のアニメーションや状態には一切触れない。
2. **足元アンカーを位置の真実とする**: `CharacterPosition` はキャラクターの下辺中央
   （足元）を表す。ウィンドウ左上は「足元 − サイズ」で毎回計算するため、サイズを何度
   切り替えても足元がずれない（丸め誤差が累積しない）。
3. **座標系は3つ、変換境界は1か所**: 座標系を「スクリーン座標」「論理座標（DIP）」
   「原寸コマ画素座標」に限定する。**スクリーン座標は、Per-Monitor DPI Aware V2 の
   プロセスにおける Win32 スクリーン座標であり、仮想スクリーン上の物理ピクセル座標と
   一致する**（この前提は `Program.cs` で DPI 認識モードを明示して固定する）。
   画面上の位置はスクリーン座標、サイズ・アンカーからのオフセット・つかみ位置・
   当たり判定・しきい値は DIP で持つ。座標系をまたぐ変換は純ロジック `CharacterLayout`
   だけが行い、`PetWindow` と `App` は「いまペットがいるモニタの表示倍率」を読んで渡すだけで
   乗除を書かない。物理サイズをキャッシュしないので、表示倍率の異なるモニタ間を移動しても
   崩れない。正式な定義は [contracts/coordinate-spaces.md](./contracts/coordinate-spaces.md)。
   なお本アプリは WPF ではなく Avalonia であり、WPF の DIU に当たるのが論理座標（DIP）。
   Avalonia ではウィンドウ位置がスクリーン座標で公開されるため、位置は DIP を経由しない。

ドラッグ中のアニメーション選択は純ロジック `DragMotionTracker`（時刻注入・UI非依存）に
切り出してユニットテストする。不要になる `BehaviorScheduler` は削除する。

## 3. 状態の4分割: Scale / Position / State / CurrentAnimation

- **Decision**: ユーザー指定に従い、次の4つを互いに独立した値として `PetWindow` の別々の
  フィールドで保持する（spec FR-023）。ウィンドウの矩形（左上座標と寸法）は保持せず、
  これらから毎回**導出**する。

  | 名称 | 実体 | 変更される契機 |
  |------|------|----------------|
  | `CharacterScale` | 列挙 `Small/Medium/Large/XLarge`（75/100/125/150%） | 常駐メニューでの選択のみ |
  | `CharacterPosition` | 足元アンカー（下辺中央）の座標 `(X, Y)` | ドラッグ、はみ出し補正、画面構成の変更 |
  | `CharacterState` | `Activity`（Idle/Dragging）＋ `Facing`（Right/Left） | ドラッグの開始/終了、左右への移動 |
  | `CurrentAnimation` | 既存の `AnimationEngine`（再生中の行＋コマ番号） | `DragMotionTracker` の判定結果、ペット切替 |

  `CharacterScale` を書き換えてレイアウトを再適用するだけで、`AnimationEngine` と
  コマタイマーには触れない。
- **Rationale**: 現状の `PetWindow` は `Window.Position`（左上・物理px）と `_mode` に
  位置と状態とアニメーションの意味が混ざっており、1つの操作（例: `SetSpriteSheet`）が
  他の値を巻き込んで初期化している。値を分けて矩形を導出にすれば、「サイズ変更で
  idle に戻る」「アニメーション切替でサイズが戻る」といった相互干渉が構造的に起きない。
  走りアニメーションの再生中にサイズが変わっても再生が続く（FR-014 / SC-011）。
- **Alternatives considered**:
  - **1つの集約クラス `Character` にまとめる**: 「別々に管理する」というユーザー指定と
    逆方向。4つは小さな値なので集約の利点も薄い。却下。
  - **`Window.Position` を位置の真実のままにする**: サイズ変更のたびに左上を
    整数pxへ丸めて書き戻すため、切替を繰り返すと足元が最大1pxずつずれていく
    （SC-010 の「ずれ1px相当以内」を累積で破る）。却下。

## 4. 座標の方針: キャラクター寸法は DIP、画面上の位置はスクリーン座標

座標系の正式な定義と変換関数の一覧は
[contracts/coordinate-spaces.md](./contracts/coordinate-spaces.md) を正とする。

- **Decision**: 座標系を「スクリーン座標」「論理座標（DIP）」「原寸コマ画素座標」の3つに
  限定し、変換は純ロジック `CharacterLayout` の1か所に集約する（spec FR-022 / FR-024）。
  - **スクリーン座標とは**: **Per-Monitor DPI Aware V2 のプロセスにおける Win32
    スクリーン座標**。この条件下では DPI 仮想化を受けないため、仮想スクリーン上の
    **物理ピクセル座標と一致する**（「物理pxか Win32 screen coordinates か」は、
    この前提のもとで同じものを指す）。原点はプライマリモニタの左上、X は右・Y は下が正、
    プライマリの左・上のモニタでは負。Avalonia の `Window.Position`・
    `Screen.WorkingArea`（`PixelPoint` / `PixelRect`）と、Win32 の `GetCursorPos` は
    すべてこの座標系の値を返す。前提の固定方法は §14。
  - **DIP で持つもの（キャラクター空間の量）**: 表示寸法（192×208 DIP × 倍率）、
    アンカーからウィンドウ左上へのオフセット（幅/2, 高さ）、ドラッグのつかみ位置
    （アンカーからカーソルへのベクトル）、当たり判定の座標、向き切替のしきい値、
    移動開始のしきい値。
  - **スクリーン座標で持つもの**: `CharacterPosition`（足元アンカー）、カーソル位置、
    作業領域、保存される位置。ロジック内では実数（double）で保持し、`Window.Position` へ
    渡す瞬間にだけ、1か所（`CharacterLayout.RoundToPixel`）で整数へ丸める。
  - **型で区別する**: スクリーン座標は `ScreenPoint` / `ScreenRect` / `CharacterPosition`、
    DIP は `DipVector` / `DipSize`。裸の `double` の組を座標として受け渡さない。
    `PetWindow` と `App` は表示倍率を読んで渡すだけで、乗除は書かない。
  - **変換に使う表示倍率**: ウィンドウが現在属するモニタの倍率（Avalonia の
    `RenderScaling`）を**毎回引数で渡す**。物理px換算の寸法はどこにもキャッシュしない。
  - **倍率が変わったとき**: `ScalingChanged`（モニタをまたいだ、または OS の表示倍率が
    変わった）を受けて、変わっていないアンカーから左上を計算し直す。ドラッグ中は
    次のポインタ移動で同じ計算が走る。
- **Rationale**:
  - ユーザー指定は「モニタ間移動で問題が起きないよう、物理ピクセルではなく DIP 基準に
    する」。問題の原因は、物理px換算した寸法やオフセットを**別のモニタの倍率のまま**使い
    続けることにある（現状コードにも、起動時に保存位置が別モニタでも
    プライマリの倍率で寸法を計算する箇所がある — `App.PositionWindow`）。
    寸法に関わる量をすべて DIP で持ち、使う瞬間に現在の倍率で換算すれば、この種の
    不整合は起きない。つかみ位置を DIP で持つので、ドラッグ中に倍率 100%→150% の
    モニタへ入っても、カーソルはキャラクターの同じ部位をつかんだままになる。
  - 一方、**画面上の位置そのもの**を DIP にすることはできない。表示倍率の異なるモニタが
    混在する環境では、デスクトップ全体で一貫する DIP 座標系が存在しない
    （DIP は「そのモニタの倍率で割った値」なので、モニタをまたぐと不連続になる）。
    デスクトップ全体で一貫しているのはスクリーン座標だけで、Avalonia の
    `Window.Position`・`Screen.WorkingArea`・カーソル座標もすべてこの座標系である。
    したがって位置の真実はこの座標系で持ち、寸法側だけを DIP にするのが、
    ユーザーの目的（モニタ間移動で崩れない）を満たす正しい分担になる。
  - **WPF との違い**: 本アプリは WPF ではなく Avalonia である（001 research.md §1）。
    論理単位の定義（1/96 インチ）は WPF の DIU と同じだが、WPF の `Window.Left/Top` が
    論理座標なのに対し、Avalonia の `Window.Position` はスクリーン座標（物理px）である。
    このため本アプリでは**ウィンドウ位置が一度も DIP を経由しない**。DIP が現れるのは
    寸法・ウィンドウ内のポインタ位置・キャラクター空間の量だけで、変換境界を
    `CharacterLayout` の1か所に絞りやすい。
  - **境界の外にある既存の変換**: 現状は `PetWindow` と `App` の計6か所で
    `LogicalWidth * RenderScaling` のような換算を直接書いている
    （一覧は contracts/coordinate-spaces.md §4「移行対象」）。すべて置き換える。
- **Alternatives considered**:
  - **位置も「px ÷ 現在モニタの倍率」の DIP で保持**: モニタをまたいだ瞬間に値が
    不連続に跳ぶ（例: x=2000px が倍率 1.0→1.5 で 2000→1333 DIP）。向き判定が
    誤反転し、位置もずれる。却下。
  - **WPF 流の「px ÷ プライマリの倍率」で保持**: 線形変換なので一貫はするが、
    プライマリの倍率を変えると保存済みの位置が別の場所を指すようになる。
    px のまま持つより脆い。却下。
  - **モニタ識別子＋モニタ内 DIP で保持**: モニタの識別が不安定（接続順・抜き差し）で、
    得るものに対して複雑すぎる。却下。

## 5. 位置の永続化: 既存キー（ウィンドウ左上・仮想スクリーン座標）を維持

- **Decision**: `settings.json` の `positionX` / `positionY` は意味を変えず、
  ウィンドウ左上の仮想スクリーン座標（物理px）のまま保存する。保存時は
  アンカーと現在のサイズ・倍率から左上を導出して書き、起動時は保存された左上と
  `scalePercent`、**その点を含むモニタの倍率**からアンカーを復元する。
  001 の契約書は単位を「DIU」と記していたが、実装は当初から物理pxを保存しており、
  本機能の契約書で実態（物理px）に合わせて記述を正す。
- **Rationale**: 保存キーを変えないので、既存の設定ファイルがそのまま使える（FR-021）。
  移行処理も不要。位置を物理pxで持つ理由は §4 のとおり。通常の利用（モニタ構成と
  倍率が前回と同じ）では、終了時と同じ矩形が正確に復元される。
- **Alternatives considered**:
  - **足元アンカーを新キーで保存**: OS の表示倍率が起動の合間に変わっても足元が
    動かない利点はあるが、新キー・旧キーからの移行・契約の改版が必要になる。
    発生頻度に対して過剰。却下（必要になれば任意キーの追加で後から対応できる）。

## 6. サイズの反映方法: ウィンドウと Image の DIP 寸法を変える

- **Decision**: サイズ変更は、ウィンドウの `Width`/`Height` と `Image` の
  `Width`/`Height` を「192×倍率, 208×倍率」DIP に設定し直して実現する。
  コマ画像（`WriteableBitmap`）は原寸 192×208 のまま使い回し、拡大縮小は描画時に行う。
  XAML の固定値 `Width="192" Height="208"` は外し、コードから設定する。
  変更時は、拡大なら「位置→寸法」、縮小なら「寸法→位置」の順に同じ UI ティック内で
  適用し、途中状態が画面外へはみ出さないようにする。
- **Rationale**: ウィンドウをキャラクターにぴったり合わせておくと、OS がウィンドウに
  割り当てるモニタ（＝適用される表示倍率）と、キャラクターが見えているモニタが一致する。
  コマ画像を複製しないのでメモリは増えない（SC-007）。Per-Monitor DPI への追従は
  001 と同じく Avalonia に任せられる。
- **Alternatives considered**:
  - **ウィンドウを最大サイズ（150%）で固定し、中の画像だけ下辺中央揃えで拡縮**:
    サイズ変更でウィンドウが動かないため、ちらつきの心配がない利点がある。
    しかし透明な余白が大きくなり、モニタ境界の近くで「ウィンドウの過半は隣のモニタ、
    キャラクターはこちらのモニタ」という食い違いが起き、隣のモニタの倍率で描画されて
    しまう。マルチモニタで崩れないというユーザー要件に反するため却下。
  - **サイズごとに拡縮済みのコマ画像を作り直す**: 9行×最大8コマ×4サイズ分のメモリと
    切替時の再生成コストがかかる。却下。
  - **Win32 `SetWindowPos` で位置と寸法を1回で変更**: 原子的だが Avalonia 内部の
    寸法状態と食い違う恐れがあり、macOS にも別実装が要る。まずは標準プロパティで実装し、
    視覚QAでちらつきが確認された場合の次善策とする。

## 7. 拡大縮小時の補間方法

- **Decision**: `Image` の `BitmapInterpolationMode` を次の規則で切り替える。
  - **Medium（100%）**: 001 と同じ `None`（最近傍）。表示は 001 と完全に同一（FR-013）。
  - **Medium 以外**: 実効倍率（サイズ倍率 × モニタの表示倍率）が整数なら `None`、
    非整数なら `HighQuality`。
  あわせて、コマ画像を作るときに**乗算済みアルファ**へ変換しておく（`AlphaFormat.Premul`）。
- **Rationale**: 最近傍補間がアーティファクトなしで成立するのは整数倍のときだけで、
  75% のような縮小では画素が間引かれて輪郭が欠け、125%・150% では画素の幅が不揃いになる
  （FR-020「輪郭のにじみ・つぶれ・欠けがない」に反する）。非整数倍では高品質補間の方が
  絵柄を保てる。Medium だけは既存の見た目を変えないことを優先する。
  乗算済みアルファにするのは、非乗算のまま補間すると透明画素の色が輪郭に混ざり、
  キャラクターの縁に暗い（または明るい）フチが出るため。
- **Alternatives considered**:
  - **常に最近傍**: 実装は最小だが、75% で輪郭が欠ける。却下。
  - **常に高品質補間**: Medium の見た目が 001 から変わる（FR-013 の趣旨に反する）。却下。
- **検証**: 最終判断は視覚QAで行う（4サイズ × 手元のモニタの表示倍率で、輪郭の欠け・
  にじみ・縁のフチを目視）。規則は `CharacterLayout` の1関数に閉じ込め、QAの結果で
  差し替えられるようにする。

## 8. はみ出し判定と位置補正

- **Decision**: サイズ変更後、キャラクターの矩形（物理px）のうち、**どのモニタの
  作業領域にも含まれない面積**が0より大きい場合に限り「はみ出し」とみなし、
  交差面積が最大のモニタの作業領域内へ最小移動で収める（既存の
  `SettingsService.ClampToScreens` を再利用）。補正した場合だけ `CharacterPosition` を
  更新し、位置を保存する。はみ出していなければ `CharacterPosition` には触れない。
- **Rationale**: spec FR-015「はみ出す場合に限り補正、はみ出さない場合は補正しない」を
  そのまま判定式にしたもの。単一モニタの作業領域への包含で判定すると、2台のモニタの
  境界にまたがって置かれたペット（両方に見えていて、はみ出してはいない）まで
  動かしてしまうため、作業領域の**和集合**に対する包含で判定する。モニタ同士は
  重ならないので、「矩形の面積 − 各作業領域との交差面積の合計」で計算できる。
  作業領域を使うのでタスクバーの下にも潜らない。
- **Alternatives considered**:
  - **常にクランプする**: ユーザーが意図して画面端に寄せた位置まで動かしてしまう。
    仕様（はみ出す場合のみ）に反する。却下。

## 9. ドラッグ中のアニメーション選択: `DragMotionTracker`

- **Decision**: UI非依存・時刻注入の純ロジック `DragMotionTracker` を新設する。
  入力はポインタ移動ごとの**移動量（DIP）**と時刻、出力は再生すべき行
  （`Idle` / `RunningRight` / `RunningLeft`）と現在の向き。規則:
  「走り出し」と「走行中の反転」は別の規則として扱う（spec FR-025）。走り出しの判定量は
  **各軸の符号つき累積変位**であり、移動の経路長でも、左右と上下を合成した距離でもない。
  斜め移動で左右・上下の累積がともに 2 DIP 未満の間は、合成距離が 2 DIP を超えていても
  `Idle` を維持する。
  - **走り出しと向きの確定**（走っていない、または向きが未確定の間）: 静止（または
    つかんだ時点）以降の左右移動の**符号つき累積** `X` が 2 DIP に達した時点で、
    **その符号から走りの向きを即時確定して**走り出す（`X ≥ +2` → `RunningRight` /
    `X ≤ −2` → `RunningLeft`）。このとき 4 DIP のヒステリシスは適用せず、保持している向き
    （前回の走行や idle 時の向き）も使わない。走りの最初のコマから移動方向と一致する
    （FR-005 / FR-006 / SC-002）。2 DIP 未満では走り出さない（押下時の手ぶれ対策）。
  - **走行中の反転**（向きの確定後だけ）: 現在の向きと逆方向への左右移動が
    **累積 4 DIP** に達したら向きを反転する。向きと同じ方向へ動いたら逆方向の累積は
    0 に戻す（ヒステリシス）。これで数ピクセル程度の左右の揺れでは向きがちらつかない
    （FR-007）。このヒステリシスを走り出しに適用してはならない。
  - **上下のみの移動**: 左右の符号つき累積が 2 DIP 未満のまま、上下の符号つき累積が
    2 DIP に達したら、保持している向きの running で走り出す（FR-008）。向きは未確定のままで、
    その後に左右の累積が 2 DIP へ達した時点で、上の規則により符号で確定する。
    上下を経路長ではなく符号つき累積（正味の移動量）で測るのは、ゆっくりした左右ドラッグに
    手の上下ぶれが混じったとき、経路長が先に 2 DIP へ達して、保持している向き
    （逆向きかもしれない）で走り出すのを防ぐため。
  - **向きの保持**: 向きは `CharacterState.Facing` に持ち、ドラッグをまたいで引き継ぐ。
    起動直後は Right。アプリの終了をまたいでは保存しない。保持している向きが使われるのは
    「上下のみの移動」の場合だけである。
  - **静止**: 最後の移動から 0.3 秒経過したら `Idle`。再び動いたら**新しい走り出し**として
    扱い（向きは未確定に戻り、累積は 0 から）、running を再開する（FR-009）。
    例: `RunningRight` → 停止 → `Idle` → 左へ 2 DIP で `RunningLeft`（前回の右向きは
    引き継がない）。`PetWindow` 側は、移動のたびに張り直す 300ms のワンショットタイマーで
    この経過を通知する。
  - **終了**: ドロップ、または `PointerCaptureLost`（画面ロック・スリープ・他操作の
    割り込み）で必ず `Idle` に戻す（FR-010）。
  移動量は「前回サンプルとの差（物理px）÷ 現在の表示倍率」で DIP に換算して渡す。
  絶対座標を DIP にして渡すと、モニタをまたいだ瞬間に値が跳んで向きが誤反転する（§4）。
- **Rationale**: 向きの判定・しきい値・0.3秒の計時は、UI から切り離せば注入した時刻で
  決定的にテストできる（001 research.md §13 の方針）。`PetWindow` に残るのは
  「位置を更新してから、トラッカーの答えどおりに行を切り替える」だけになる。
  位置の更新を先に行うので、アニメーションの切替がカーソルへの追従を遅らせない（FR-011）。
- **行の切替**: トラッカーの答えが現在の行と同じなら何もしない（同じ行を再指定して
  コマ0に戻すと、走りが足踏みのように見える）。`AnimationEngine.SwitchTo` の
  「切替時はコマ0から」という既存の意味は変えず、呼ぶ側で比較する。
- **Alternatives considered**:
  - **走り出しにも 4 DIP の反転ヒステリシスを適用する（当初案）**: 保持している向きと
    逆へ動かすと、走り出しの 2 DIP から反転の 4 DIP までの間だけ、逆向きの走りが
    表示される（例: 向きが Right のまま左へドラッグ → 右向きで走り出してから左向きへ
    切り替わる）。停止後に逆向きへ再開するときも同じ。FR-005 / FR-006 / SC-002 に反し、
    FR-007 が禁じるちらつきそのものになる。規則のシミュレーションでも、この案は
    逆向きのコマが出ることを確認した。却下。
  - **上下の走り出しを経路長（移動量の合計）2 DIP で判定する**: 左右の規則を上のとおり
    直しても、ゆっくりした左右ドラッグに上下の手ぶれが混じると、経路長が先に 2 DIP へ達し、
    保持している向きで走り出してしまう（シミュレーションで逆向きのコマを確認）。
    符号つき累積で測れば起きない。却下。
  - **直近1サンプルの符号だけで向きを決める**: 1pxの揺れで左右が切り替わりちらつく。却下。
  - **速度ベース（px/秒）の判定**: サンプル間隔に敏感で調整が難しい。累積距離の
    ヒステリシスの方が単純で、テストもしやすい。却下。
  - **定期ポーリングで静止を検出**: ドラッグ中ずっとタイマーが回る。移動のたびに
    張り直すワンショットの方が無駄がない。却下。

## 14. DPI 認識モードを Per-Monitor V2 に明示的に固定する

- **Decision**: `Program.BuildAvaloniaApp` に
  `.With(new Win32PlatformOptions { DpiAwareness = Win32DpiAwareness.PerMonitorDpiAware })`
  を追加し、DPI 認識モードを明示的に指定する。起動時に現在のスレッドの DPI 認識モードを
  調べ、Per-Monitor V2 でなければ診断ログへ記録する（クラッシュはさせない）。
- **Rationale**: §4 の「Win32 スクリーン座標 = 物理ピクセル座標」は、プロセスが
  Per-Monitor DPI Aware V2 のときにだけ成り立つ。Unaware や System DPI Aware では
  Win32 が返す座標が OS に仮想化（拡縮）され、`GetCursorPos` と `Window.Position` と
  実際の画素がずれる。調査の結果、本アプリにはアプリケーションマニフェストがなく、
  DPI 認識モードは Avalonia の既定値に任されていた（Avalonia.Win32 11.3.22 は
  `SetProcessDpiAwarenessContext` → `SetProcessDpiAwareness` → `SetProcessDPIAware` の
  順で適用し、既定は `PerMonitorDpiAware`）。既定値は現状でも正しいが、座標系の定義の
  成立条件をフレームワークの既定値に依存させないため、コードで明示する。
  P/Invoke の `GetCursorPos` も同じプロセスの認識モードで動くので、Avalonia の値と
  同じ座標系になる。起動時のログは、exe のプロパティの「高 DPI 設定の変更」で
  上書きされた場合などに原因へ辿り着けるようにするためのもの。
- **Alternatives considered**:
  - **既定値に任せる（現状維持）**: 動作は同じだが、前提が暗黙のままになる。Avalonia の
    更新や設定変更で崩れても気付けない。却下。
  - **アプリケーションマニフェストで宣言**: Win32 としては正攻法だが、Avalonia の
    オプションと二重管理になる。Avalonia のオプション1行で足りる。却下。

## DragMotionTracker（ドラッグ中のアニメーション判定）【新規】

`Animation/DragMotionTracker.cs`。UI非依存・時刻注入の純ロジック。ドラッグ1回ごとに
`Begin` → `Move`×n →（`Poll`）→ `End` の順で使う。

| 定数 | 値 | 根拠 |
|------|----|------|
| `MoveStartThresholdDip` | 2 DIP | 走り出しと、走り出し時の向きの確定に使う。押下時の手ぶれで走り出さない |
| `FlipThresholdDip` | 4 DIP | **走行中（向き確定後）の反転にだけ**使う。数ピクセル程度の揺れで向きを反転しない（FR-007） |
| `StillnessTimeout` | 300 ms | 0.3秒静止で idle（FR-009） |

| 内部状態 | 説明 |
|---------|------|
| `Facing` | 現在の向き。`Begin` で `CharacterState.Facing` を受け取り、変化を呼び出し側へ返す |
| `IsRunning` | 走り中か（走り出しのしきい値を越えたか） |
| `IsDirectionCommitted` | 今回の走り（静止または開始以降）の向きを、**左右の移動によって確定したか**。false の間は反転ヒステリシスを適用しない |
| `netXSinceStill` | 静止（または開始）からの左右移動の**符号つき**累積（DIP）。右が正 |
| `netYSinceStill` | 静止（または開始）からの上下移動の**符号つき**累積（DIP） |
| `oppositeTravel` | 向きの確定後、現在の向きと逆方向への左右移動の累積（DIP） |
| `lastMoveAt` | 最後に移動を受け取った時刻 |

| 操作 | 入力 | 出力 / 効果 |
|------|------|-------------|
| `Begin(facing, now)` | 現在の向き・時刻 | `IsRunning = false`、`IsDirectionCommitted = false`、累積をすべて 0 に。出力 `Idle` |
| `Move(dxDip, dyDip, now)` | 前回からの移動量（DIP）・時刻 | 累積を更新。向き未確定なら「走り出しと向きの確定」、確定済みなら「走行中の反転」の規則を適用し、再生すべき行を返す |
| `Poll(now)` | 時刻 | `now − lastMoveAt ≥ 300ms` なら `IsRunning = false`・`IsDirectionCommitted = false`・累積をすべて 0 にして `Idle`、未満なら現在の行 |
| `IsStill(now)` | 時刻 | `now − lastMoveAt ≥ 300ms` か。状態は変えない。`PetWindow` のワンショットタイマーがわずかに早く発火した場合に、0.3秒へ達するまで確かめ直すために使う |
| `End()` | – | `Idle` を返す。`Facing` は保持したまま |

移動量が 0 の `Move`（同じ位置のポインタイベント）は移動として数えず、`lastMoveAt` も更新しない。

        ▼                                                     ▼           │
   ┌──────────────────────────┐  Move: |netX| ≥ 2 DIP     Facing を反転 ──┘
   │ Running（向き未確定）       │ ───────────────────────▶ （Running のまま）
   │ 保持している向きの running  │  向き = netX の符号
   └──────────────────────────┘  （即時確定・ヒステリシスなし）

   End（ドロップ/中断）はどの状態からでも Idle へ。Poll の 300ms 無移動も、どの Running からでも Still へ。
` ` `

「走り出し」と「走行中の反転」は別の規則である。4 DIP のヒステリシスを走り出しに
適用してはならない（適用すると、保持している向きと逆へ動かしたとき、2〜4 DIP の間だけ
逆向きの走りが表示される）。

- **走り出しと向きの確定**（`IsDirectionCommitted = false` の間。`Move` のたびに
  `netXSinceStill += dx`、`netYSinceStill += dy` としてから、次の順で判定する）:
  1. `|netXSinceStill| ≥ 2 DIP` なら、**その符号で向きを即時確定する**
     （`≥ +2` → `Right` / `≤ −2` → `Left`）。`IsDirectionCommitted = true`、
     `IsRunning = true`、`oppositeTravel = 0`。保持している向き（前回の走行や idle 時の向き）は
     この判定に**使わない**。4 DIP のヒステリシスも適用しない。したがって走りの
     **最初のコマから**移動方向と同じ向きになる（FR-005 / FR-006 / SC-002）。
  2. 1 に該当せず `|netYSinceStill| ≥ 2 DIP` なら、上下のみの移動とみなし、
     **保持している向き**で走り出す（`IsRunning = true`、FR-008）。向きは未確定のままとし、
     その後 `|netXSinceStill|` が 2 DIP に達した時点で 1 により確定する。
  3. どちらにも該当しなければ `Idle` のまま。判定量は**各軸の符号つき累積変位**であり、
     経路長でも合成距離でもない（spec FR-025）。したがって、斜めに動かして
     `|netX| < 2` かつ `|netY| < 2` の間は、合成距離 `√(netX² + netY²)` が 2 DIP を
     超えていても `Idle` を維持する（例: `(−1.5, +1.5)` は合成距離 約2.12 DIP だが `Idle`）。
- **走行中の反転**（`IsDirectionCommitted = true` の間だけ）: `dx` が現在の向きと同じ符号なら
  `oppositeTravel = 0`。逆の符号なら `oppositeTravel += |dx|` とし、4 DIP に達したら
  `Facing` を反転して 0 に戻す。4 DIP 未満の逆方向の揺れでは向きを変えない（FR-007）。
  `dx = 0`（上下のみ）のときは向きに触れない（FR-008）。
- **停止後の再開**: `Poll` で `Idle` に戻った後の移動は、新しい走り出しとして扱う
  （向きは未確定に戻り、累積は 0 から）。例: `RunningRight` → 停止 → `Idle` → 左へ 2 DIP で
  `RunningLeft`。前回の右向きは引き継がない。
- 保持している向き（`Facing`）が使われるのは、上の 2（左右の累積が 2 DIP 未満の
  上下移動）の場合だけである。左右へ 2 DIP 動いた時点で、必ず移動の符号に置き換わる。
- 上下の走り出しを経路長ではなく**符号つき累積**（正味の移動量）で判定するのは、
  ゆっくりした左右ドラッグに手の上下ぶれが混じったとき、経路長が先に 2 DIP へ達して
  保持している向き（＝逆向きかもしれない向き）で走り出すのを防ぐためである。
  その場での小刻みな揺れでも走り出さない。
- 移動量は「物理pxの差 ÷ 現在の表示倍率」で DIP に換算して渡す。絶対座標は渡さない
  （モニタをまたぐと DIP の絶対値が不連続になるため。research.md §9）。

001 の契約書は `positionX` / `positionY` の単位を「DIU」と記していたが、実装は当初から

# Contract: 座標系と変換境界

**Type**: 内部契約（アプリ内のすべてのコードが従う座標系の定義）
**対応する要求**: spec FR-022 / FR-024、research.md §4・§14

本アプリが扱う座標系は次の**3つだけ**である。どの値がどの座標系に属するかを型で区別し、
座標系をまたぐ変換は `CharacterLayout` の1か所に限定する。

> **用語について**: 本アプリの UI フレームワークは WPF ではなく **Avalonia UI** である
> （001 research.md §1 で WPF から変更済み）。WPF でいう「WPF 座標（DIU）」に当たるものは、
> 本書の **論理座標（DIP）** である。単位の定義（1/96 インチ）は WPF と同じだが、
> 後述のとおり**ウィンドウ位置の扱いが WPF と異なる**点に注意する。

## 1. スクリーン座標（Screen px）

**定義**: **Per-Monitor DPI Aware V2 のプロセスにおける Win32 スクリーン座標
（screen coordinates）**。この条件下では Win32 のスクリーン座標は DPI 仮想化を受けないため、
**仮想スクリーン（全モニタを連結した領域）上の物理ピクセル座標と完全に一致する**。
つまり本アプリでは「Win32 スクリーン座標」と「物理ピクセル座標」は同じものを指し、
その同一性を成り立たせる前提（DPI 認識モード）を §5 でコードにより固定する。

| 項目 | 内容 |
|------|------|
| 原点 | **プライマリモニタの左上**が (0, 0) |
| 軸 | X は右が正、Y は下が正 |
| 負の値 | プライマリより左・上に配置されたモニタ上では負になる（正常な値） |
| 単位 | 1 = その点があるモニタの物理ピクセル1個。座標の格子は全モニタで連続している |
| 表示倍率の影響 | **受けない**。モニタの表示倍率を変えても、同じ場所の座標は変わらない |
| Avalonia での型 | `PixelPoint` / `PixelRect`（整数） |
| 本アプリでの型 | `ScreenPoint` / `ScreenRect` / `CharacterPosition`（実数） |

この座標系に属する値:

| 値 | 取得元 / 設定先 |
|----|----------------|
| ウィンドウ左上 | Avalonia `Window.Position`（Win32 `SetWindowPos` / `GetWindowRect` と同じ値） |
| モニタの全体領域・作業領域 | Avalonia `Screen.Bounds` / `Screen.WorkingArea`（Win32 `MONITORINFO.rcMonitor` / `rcWork`） |
| カーソル位置 | `IWindowEffects.TryGetCursorPosition`（Win32 `GetCursorPos`） |
| キャラクターの位置 | `CharacterPosition`（足元アンカー） |
| 保存される位置 | `settings.json` の `positionX` / `positionY` |

**デスクトップ全体で一貫しているのはこの座標系だけ**である。したがって「画面上のどこか」を
表す値は、必ずこの座標系で持つ。

## 2. 論理座標（DIP）

**定義**: Avalonia の論理単位。**1 DIP = 1/96 インチ**（表示倍率 100% のとき物理ピクセル1個）。
WPF の DIU と同じ定義である。

| 項目 | 内容 |
|------|------|
| 原点 | **ウィンドウのクライアント領域の左上**（ウィンドウローカル）。または原点を持たない長さ・ベクトル |
| 物理ピクセルとの関係 | `px = DIP × 表示倍率`（表示倍率 = 1.0 / 1.25 / 1.5 / 2.0 …） |
| 本アプリでの型 | `DipVector` / `DipSize`（実数） |

この座標系に属する値:

| 値 | 取得元 / 設定先 |
|----|----------------|
| ウィンドウ・画像の寸法 | Avalonia `Window.Width/Height`、`Image.Width/Height` |
| ウィンドウ内のポインタ位置 | Avalonia `PointerEventArgs.GetPosition(window)` |
| キャラクターの表示寸法 | `CharacterLayout.SizeDip(scale)` = (192, 208) × サイズ倍率 |
| アンカー → ウィンドウ左上のオフセット | (幅/2, 高さ) |
| ドラッグのつかみ位置 | アンカーからカーソルへのベクトル |
| しきい値 | 走り出し 2 DIP、向き反転 4 DIP |

**DIP をデスクトップ全体の位置として使ってはならない**。表示倍率の異なるモニタが混在すると、
DIP の絶対座標はモニタの境界で不連続になる（例: x = 2000 px は倍率 1.0 で 2000 DIP、
倍率 1.5 で 1333 DIP）。DIP は常に「ウィンドウローカルの位置」か「長さ・ベクトル」として使う。

### WPF との違い（混同しやすい点）

| | WPF | Avalonia（本アプリ） |
|--|-----|----------------------|
| ウィンドウ位置 | `Window.Left/Top` は **DIU**（論理座標） | `Window.Position` は **スクリーン座標（物理px）** |
| ウィンドウ寸法 | `Width/Height` は DIU | `Width/Height` は DIP（同じ） |
| 帰結 | 位置をスクリーン座標と突き合わせるたびに変換が要る | **位置は一度も DIP を経由しない**。DIP が現れるのは寸法・ウィンドウ内位置・キャラクター空間の量だけ |

## 3. 原寸コマ画素座標（Source px）

**定義**: スプライトアトラスの1セル（192×208）内の画素座標。原点はセルの左上、
範囲は X: 0〜191、Y: 0〜207。

| 項目 | 内容 |
|------|------|
| DIP との関係 | `ウィンドウローカル DIP = Source px × サイズ倍率`（サイズ倍率 = 0.75 / 1.0 / 1.25 / 1.5） |
| 属する値 | アルファマップ（クリック透過の当たり判定）、コマ画像の画素 |

## 4. 変換境界

### 規則

1. **座標系をまたぐ変換は `Services/CharacterLayout.cs` の純関数だけが行う。**
   `PetWindow` と `App` は、表示倍率とサイズ倍率を**読んで引数として渡すだけ**とし、
   表示倍率・サイズ倍率による乗算・除算を自分では書かない。
2. **型で座標系を区別する。** スクリーン座標は `ScreenPoint` / `ScreenRect` /
   `CharacterPosition`、DIP は `DipVector` / `DipSize`。裸の `double` の組を
   座標として受け渡さない（どの座標系か分からなくなるため）。
3. **使う表示倍率は「ウィンドウが現在属するモニタ」の倍率**（Avalonia `RenderScaling`。
   Win32 の `GetDpiForWindow ÷ 96` と同じ値）。例外は起動時の位置復元だけで、ウィンドウを
   表示する前なので、保存位置の点を含むモニタの `Screen.Scaling` を使う。
   物理ピクセルに換算した寸法を**キャッシュしない**（必ず使う直前に換算する）。
4. **丸めは1か所。** スクリーン座標はロジック内では実数で保持し、整数への丸めは
   `Window.Position` へ代入する直前の `CharacterLayout.RoundToPixel` だけで行う
   （四捨五入、`MidpointRounding.AwayFromZero`）。丸めた値を位置の真実へ書き戻さない。
5. **移動量は差分で DIP に換算する。** ドラッグの移動量は「スクリーン座標の差 ÷ 表示倍率」
   で求める。スクリーン座標の絶対値を DIP に換算して差を取ってはならない
   （モニタをまたいだ瞬間に値が跳ぶ）。

## 5. 前提: DPI 認識モードの固定

§1 の「Win32 スクリーン座標 = 物理ピクセル座標」は、プロセスが
**Per-Monitor DPI Aware V2** である場合にだけ成り立つ。DPI 非対応（Unaware）や
System DPI Aware のプロセスでは、Win32 が返すスクリーン座標は OS により仮想化（拡縮）され、
物理ピクセルと一致しない。

- **固定方法**: `Program.BuildAvaloniaApp` で
  `Win32PlatformOptions { DpiAwareness = Win32DpiAwareness.PerMonitorDpiAware }` を
  **明示的に指定する**。Avalonia 11.3 の既定値も同じだが、本契約の成立条件を
  フレームワークの既定値に依存させない（Avalonia はこの指定を
  `SetProcessDpiAwarenessContext(PER_MONITOR_AWARE_V2)` で適用する）。
- **P/Invoke への波及**: `GetCursorPos` などの直接呼び出しも同じプロセスの DPI 認識モードで
  動くため、Avalonia の `Window.Position` と同じ座標系の値を返す。
- **起動時の確認**: 起動時に現在のスレッドの DPI 認識モードを調べ、Per-Monitor V2 で
  なければ診断ログに記録する（exe のプロパティの「高 DPI 設定の変更」で上書きされた場合
  などに気付けるようにする。クラッシュはさせない）。

## 6. macOS（ベストエフォート）

macOS では Avalonia が画面座標を「左上原点・下向き正の `PixelPoint`」に正規化して公開する。
本契約の「スクリーン座標」は、macOS では **Avalonia の `Window.Position` が属する座標系**と
定義する。`MacWindowEffects.TryGetCursorPosition` は、OS から得たカーソル位置（左下原点の
ポイント単位）を、この座標系へ変換して返す責任を負う。
すなわち `IWindowEffects.TryGetCursorPosition` の契約は、どの OS でも
「**`Window.Position` と同じ座標系でカーソル位置を返す**」である。検証は Windows で行う。
